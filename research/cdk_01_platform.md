**Nesting (as documented across the above sources):** Dealer/CMF (contract & billing entity) → one or more Company Numbers/stores (legacy accounting layer) → per-store Fortellis Subscription-Id → per-subscription set of Department-IDs, each scoped to one DMS type (Accounting/Finance/Inventory/Parts/Service). A given API call always carries **Subscription-Id** (which store/tenant) + **Department-Id** (which module within that store) + Authorization + Request-Id.

`UNVERIFIED`: Whether "Company Number" is formally exposed anywhere in the modern Fortellis REST layer as its own field/header, or whether it is purely a legacy back-office/EDI-era concept superseded by Subscription-Id + Department-Id in the API surface. No Fortellis spec found that names a `Company-Number` header.

## 3. Fortellis: ownership, subscription flow, header contract

- Fortellis (full name "Fortellis Automotive Commerce Exchange") is **owned and operated by CDK Global**; launched March 2018 at NADA Las Vegas as an API gateway, Developer Network, and Marketplace for the automotive retail industry. [BusinessWire launch release](https://www.fi-magazine.com/323813/cdk-global-launches-fortellis-automotive-commerce-exchange-platform), [Built In Chicago](https://www.builtinchicago.org/articles/cdk-global-fortellis-automotive-industry-api-marketplace).
- Two sides: the **Developer Network** (build/certify apps, browse API Directory) and the **Marketplace** (dealers discover/activate apps). [Fortellis platform docs](https://docs.fortellis.io/docs/general/ecosystem/introduction/), [CDK Connect 2023 session](https://www.youtube.com/watch?v=czyOfweYgoM).
- Subscription flow: developer registers an App in the Developer Network → selects APIs/bundles and a pricing plan → dealer discovers app in Marketplace and activates a subscription → Fortellis issues a **Subscription-Id** binding that dealer (store) to that app; app publishers can pull Subscription-Id values programmatically or via the Subscription Report. [Fortellis "Accepting Subscription Activation Requests"](https://docs.fortellis.io/docs/tutorials/admin-api/accepting-subscription-requests/), [Fortellis "App Listing Guide"](https://community.fortellis.io/sites/default/files/Fortellis_App.Listing.Guide_.pdf).
- **Three-header contract**, confirmed identically across multiple CDK Drive API specs:

| Header | Requirement | Function |
|---|---|---|
| `Authorization` | REQUIRED | `Bearer <token>` from Fortellis OAuth 2.0 Client Credentials flow via the Fortellis identity server |
| `Subscription-Id` | REQUIRED | Identifies the dealer/store-app subscription making the call |
| `Request-Id` | REQUIRED | Client-generated UUID correlation ID, echoed back in the response |

Sources: [CDK Drive Get Customer v3 developer guide](https://fortellis-api-documents-prod.s3-us-west-2.amazonaws.com/f83a79c6-8cf9-4c1a-b45e-b266634eaf90/external/20251119155158640--ZuFlj8i.pdf), [Fortellis Repair Orders v1 reference](https://community.fortellis.io/api-reference/vehicle-service/cdkdrive-repair-orders/cdkdrive-repair-orders-v1/get/%7BrepairOrderId%7D), [Elead CRM OpenAPI spec](https://raw.githubusercontent.com/api-evangelist/elead-crm/refs/heads/main/openapi/elead-crm-openapi.yml).

- **CDK-specific fourth header**: `Department-Id` — REQUIRED on CDK Drive APIs specifically (not a generic Fortellis-wide header; it is CDK's own DMS-partition mechanism layered on top of the platform contract). [CDK Drive Get Customer v3 spec](https://fortellis-api-documents-prod.s3-us-west-2.amazonaws.com/f83a79c6-8cf9-4c1a-b45e-b266634eaf90/external/20251119155158640--ZuFlj8i.pdf).
- Async/event APIs additionally use `X-Request-Id` in the AsyncAPI (event relay) contract. [Fortellis Event Relay Data Plane AsyncAPI spec](https://apis.io/asyncapis/cdk-global/fortellis-event-relay-data-plane-proxy-asyncapi/).
- Platform scale (self-reported/aggregator, 2023–2026): 100+ public/private APIs, 200+ marketplace apps, 12,000+ active subscriptions (2023); later figures cite 135+ published APIs, 425+ marketplace apps, 82,000+ dealer integrations, 6.7B+ annual transactions. [CDK Connect 2023 breakout](https://www.youtube.com/watch?v=czyOfweYgoM), [APIs.io CDK Global provider page](https://apis.io/providers/cdk-global/).

## 5. Third Party Access (3PA): cost, friction, litigation

**3PA mechanics.** 3PA is CDK's official/contractual product for third-party vendors to obtain automated data access to a dealer's DMS; per litigation records it is "the only approved method for accessing" CDK DMS data, and CDK "contractually forbids vendors from obtaining data from anyone but CDK." [Hoover Automotive v. CDK Global complaint](https://www.classaction.org/media/hoover-automotive-v-cdk-global.pdf).

**What it proves for the twin's design rationale:** a single-vendor, single-tenant hosted DMS architecture (CDK Drive) with no dealer-side redundancy meant that ~15,000 independently owned dealerships — including whole functional domains (sales, service, parts, payroll, registration) — went dark simultaneously for two weeks with no failover path except manual paper processes, because the DMS is both the system of record and the only path to that record. This is the direct architectural justification for a sovereign, dealer-owned twin that can independently retain and reconstruct operational data (SAP-shape tables) rather than depending solely on CDK's own systems being up.

## Proposed SAP-shape mapping

| CDK Drive / Fortellis concept | Proposed SAP object in the twin | Rationale |
|---|---|---|
| Dealer ID / CMF (top-level client) | New table analogous to **T001W**-style plant/company-code master, or a dedicated `EVE_DEALER` root entity | Anchors the whole tenant; not itself an SAP MM object since it's above plant level |
| Company Number (per-store legal/accounting entity) | **T001** (Company Code) per rooftop, or **WERKS** (Plant) if modeled at plant granularity | Matches "one store = one accounting entity" pattern from Mitchell/CDK docs |
| Department ID (DMS-type-scoped: Accounting/Finance/Inventory/Parts/Service) | Cross-module scoping flag alongside **MARC** (plant data) / **MARD** (storage location) records, tagged by functional module | Department-Id filters *which module's* data a call returns — closest SAP analogue is module + plant/storage-location scoping, not a single table |
| Subscription-Id (Fortellis app↔store binding) | Interface/integration control table (not a standard MM master table) — track as `EVE_API_SUBSCRIPTION` mapping app, store (WERKS), and department | No native SAP MM equivalent; this is an integration-layer artifact specific to the twin's API gateway, tracked separately from goods-movement tables |
| Parts Sales / Parts Inventory (CDK Drive Get Parts Sales, Parts Store API) | **MARA** (material master), **MARC** (plant data), **MARD** (storage location stock), **MBEW** (valuation), **MATDOC** (material document/movements) | Direct match to the existing eve-dealer-parts-twin shape |
| Parts pricing (Get Parts Sales pricing fields) | **MVKE** (sales data) / **MFRPN** (manufacturer part number) | Matches existing twin fields already in use |
| Repair Order / Service (CDK Drive Repair Order, Workshop Management, Op Codes) | New service-order shape modeled analogous to SAP CS/PM order tables (outside current MM scope) — propose `EVE_SVC_ORDER` header/line tables mirroring MATDOC's movement-document pattern for labor/parts consumption | Repair orders consume parts (→ MATDOC) and post labor (→ new table); needs its own header/line structure since SAP MM alone has no service-order object |
| Customer (CDK Drive Customers API) | New `EVE_CUSTOMER` master outside MM scope (SAP equivalent would be **KNA1** business-partner in SD, not MM) | Customer master doesn't belong in the MARA/MARC parts shape; flag for a future SD-shape lane |
| F&I Sales / Deals (FI Sales Setup/Bulk/Delta) | New `EVE_DEAL` header/line table set, referencing vehicle inventory and customer objects | No MM analogue; vehicle sales are outside parts-inventory shape entirely |
| Vehicle Inventory (Get Make Model Lite, Vehicle Specifications) | Vehicle-specific master parallel to **MARA**, e.g. `EVE_VEHICLE_MASTER` (VIN-keyed) since vehicles are serialized units, not stockable parts | Vehicles need serial/VIN-level tracking that MARA's generic-material model does not natively support without extension |
| Accounting GL extracts (CDK Get Customer v3 "Accounting DMS type", Payroll package Accounting GL) | Standard FI tables (outside MM) — flag for accounting lane, not parts lane | Confirms this lane's scope boundary: accounting data flows to a separate FI-shape mapping, not MARA/MARC |
| Async long-operation pattern (History Setup → Bulk → Delta) | Integration/staging tables (`EVE_STAGING_*`) feeding into MATDOC-style movement documents only after reconciliation | The twin needs an explicit staging layer to replicate CDK's async poll-and-pull pattern before writing into SAP-shape target tables |
