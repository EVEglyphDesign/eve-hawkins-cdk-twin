# Lane C — What Is "the PACCAR Platform," and Where Are Its Edges?

## Summary: what I found and what I didn't

The "PACCAR platform" is not one system — it is a federation of at least five distinct, separately-branded systems (PACCAR Solutions/Decisiv, SmartLINQ/TruckTech+ telematics, PACCAR Parts/MDI/OPC, PRWS warranty, and PACCAR's internal SAP estate) stitched together by OEM-controlled integrations, mostly reaching the dealer only through the dealer's own DMS vendor (CDK Drive/Fortellis, Procede Excede, or Karmak Fusion). PACCAR does publish a real, token-gated developer API catalog (`developers.paccar.cloud`) for "Connected Truck APIs," and Decisiv separately publishes its own SRM API documentation — so an API surface genuinely exists, but it is licensed, revocable, and scoped to interoperation, not open data access. I found solid, PACCAR/Peterbilt/Kenworth/Decisiv-published evidence for items 1–4 and 6. On SAP (item 5), I found strong, verifiable evidence PACCAR runs SAP for finance, HCM, IBP/supply chain, GTS and logistics — but found **no public evidence** of SAP Datasphere, SAP BTP, or SAP Business Network use; this is a genuine gap, not an oversight. Warranty claim data flow (PRWS, VMRS/SRT coding, SIR) is the best-documented single thread in this lane. The "last mile" gap (item 7) is stated directly from the evidence collected, not invented.

## 1. PACCAR Solutions — the connected-truck/fleet portal

**What it is.** PACCAR Solutions (`www.PACCARSolutions.com`) is PACCAR's unified web portal for fleet health, service scheduling, warranty/recall visibility, and telematics subscription management across Peterbilt and Kenworth. Peterbilt's own sales material describes it as providing "real-time access to fleet health and diagnostics," a "centralized location for scheduling and monitoring services performed at Peterbilt dealerships, including the ability to receive and approve electronic estimates," plus "service history, warranty and preventive maintenance schedules" ([Peterbilt Connected Truck Technologies sales sheet](https://www.peterbilt.com/static-assets/documents/resources/smartlinq_sales_sheet.pdf)).

**Who built it and what runs underneath.** Decisiv's own site states plainly: "The PACCAR Solutions Service Management (PSSM) platform is developed by Decisiv for PACCAR. The Decisiv platform streamlines the entire service lifecycle through digital communication between service providers and fleets" ([Decisiv — PACCAR Solutions](https://paccar.decisiv.net/)). The PACCAR Solutions login is itself hosted on Decisiv's domain (`paccar.decisiv.net`), and PACCAR Solutions help documentation is hosted at `support.paccar.decisiv.net`.

**What data it holds.** Per Peterbilt/Kenworth material and PACCAR Solutions' own help articles: VIN, unit number, fault/diagnostic codes (up to ~900 codes monitored), fault severity level (Stop Now / Service Now / Service Soon / Informational), vehicle location, dealer/service-center assignment, service case status, warranty and recall status, and — via the "Create a Service Request" flow — VMRS codes, driver name/phone/email, breakdown location, purchase-order numbers, and file attachments ([PACCAR Solutions — Create a Service Request](https://support.paccar.decisiv.net/hc/en-us/articles/360026414033-Create-a-Service-Request); [Peterbilt SmartLINQ Operators Manual](https://www.peterbilt.com/static-assets/documents/resources/smartlinq_operators_manual.pdf)).

**Who can see what.** Access is role-based: fleets/customers see their own trucks; the truck's designated "Primary Care Provider" (owner, fleet manager, or dealer) receives notifications; dealers gain visibility to a customer's trucks only if the customer or selling dealer explicitly grants it — a Kenworth how-to video instructs users to "join the Peterbilt and Kenworth dealer Network under dealer monitoring — this will provide all Peterbilt/Kenworth dealers with visibility to your trucks" ([How to use PACCAR Solutions – Left Hand Menu](https://www.youtube.com/watch?v=yKOxGtipLiI)). This is opt-in dealer monitoring, not default OEM-to-dealer data sharing.

**API / developer program / data export.** PACCAR does publish a formal, contractual API program: the **PACCAR API License Agreement** governs "Connected Truck APIs" catalogued at `developers.paccar.cloud`, described as PACCAR's "centralized discovery of PACCAR API products" for "secure, seamless integration between different systems and applications, allowing for the exchange of PACCAR data and functionality" ([PACCAR Digital Services Terms / API License Agreement](https://developers.paccar.cloud/ — NOTE 2026-07-29: the canonical paccar.com/digital-services-terms/ page 404s; licence wording above came from a pre-production copy and is indicative only)). Access requires an API Token, is "limited, revocable, non-exclusive, non-transferable," restricted to "internal business purposes," fee-bearing under a Subscription Order Form, and can be revoked by PACCAR "at any time." This confirms a real API surface exists, but it is a licensed, gated program, not open/public data access. Separately, the underlying reporting/portal layer supports Excel export and scheduled email delivery of fleet reports and "advanced analytics" (campaign status, DTC reports, subscription details) ([PACCAR Solutions — Utilize New Reports](https://www.youtube.com/watch?v=iSMjZey8Axk)). I could not find a published OpenAPI spec, rate limits, or self-serve signup flow for the PACCAR API Catalog itself (the catalog page returned access-restricted when fetched directly); the terms document is the only primary-source detail available.

**Adjacent platforms sharing the "PACCAR Solutions" brand internationally.** DAF/PACCAR Australia markets an analogous but distinct product, "PACCAR Connect," described by DAF as "an open, secure API that integrates multiple data sources on a single user interface," with a formal "Data Integration Partner Program" application form ([DAF PACCAR Connect Partners](https://www.daf.com/en/products-and-services/daf-services/connected-services/paccar-connect-partners); [PACCAR Connect brochure](https://www.scribd.com/document/735471635/PACCAR-Connect-brochure-EN)). PACCAR Connect is **not** the platform used by Peterbilt/Kenworth in North America — North America uses PACCAR Solutions/SmartLINQ/TruckTech+. This distinction matters: marketing material sometimes blurs the two.

## 2. SmartLINQ (Peterbilt) and TruckTech+ (Kenworth) remote diagnostics

**What they emit.** Both are OEM-branded names for the same underlying PACCAR remote-diagnostics architecture, differing only by brand. Peterbilt's own operators manual describes the full chain: "SmartLINQ immediately communicates with PACCAR's back office by wirelessly sending detailed data about the event. PACCAR's back office system translates the data into user-friendly text and graphics, and generates PACCAR Solutions web portal and email notifications" ([Peterbilt SmartLINQ Operators Manual](https://www.peterbilt.com/static-assets/documents/resources/smartlinq_operators_manual.pdf)). SmartLINQ monitors 800–900+ engine and aftertreatment diagnostic codes and classifies each into four severity tiers ([Peterbilt Connected Services](https://www.peterbilt.com/why-peterbilt/connected-services)). Kenworth's TruckTech+ is functionally identical: "the data is sent to the secure PACCAR Solutions web portal where the fleet manager can review the truck's location, status, identified issue and recommended solution" ([Kenworth TruckTech+ press release](https://www.kenworth.com/about-us/news/kenworth-trucktech-remote-diagnostics-available-as-option-for-kenworth-new-medium-duty-models/)).

**Over what channel.** An onboard modem (historically a PeopleNet Mobile Gateway, per an NHTSA-hosted Peterbilt technical bulletin describing a "SmartLINQ Communication Modem" replacement campaign) wirelessly transmits event data to PACCAR's back-office ([NHTSA TSB MC-10136225](https://static.nhtsa.gov/odi/tsbs/2018/MC-10136225-9999.pdf)).

**Into which back end.** All fault event data lands in "PACCAR's back office," which generates the notifications and portal content surfaced via PACCAR Solutions/Decisiv (see §1). Both SmartLINQ and TruckTech+ explicitly funnel into the same PACCAR Solutions portal — there are not two separate diagnostics back ends for Peterbilt vs Kenworth. In 2020, PACCAR added "reasoning engine technology" — machine learning that correlates fault codes using field repair data — described as sitting on top of the same SmartLINQ data stream ([Truck News](https://www.trucknews.com/products/reasoning-engine-technology-added-to-smartlinq/)).

**What the dealer actually sees.** The dealer does **not** see a raw telemetry stream. It sees the same processed portal view as the fleet: plain-English fault descriptions, troubleshooting steps, severity classification, and nearest-dealer recommendations, as delivered through PACCAR Solutions ([Peterbilt Connected Services](https://www.peterbilt.com/why-peterbilt/connected-services)). Dealer access to a specific customer's trucks is opt-in via "dealer monitoring," not automatic dealer visibility to all diagnostics. There is a further dealer-side integration path: PACCAR's own field service bulletin confirms that Kenworth, working with **Decisiv and Noregon**, built an integration allowing dealers to submit vehicle check-in data (VIN, mileage, faults, diagnostic parameters) directly from Noregon's **JPRO Professional** diagnostic tool into a PACCAR Solutions case — this is diagnostic-tool-to-case automation, not raw telemetry access ([NHTSA-hosted Kenworth Technical Information Bulletin](https://static.nhtsa.gov/odi/tsbs/2019/SB-10161170-9999.pdf)).

**Third-party telematics aggregation.** As of 2017, PACCAR Solutions was reported to already aggregate data from "20 telematics service providers" into one dashboard ([Fleet Equipment Magazine](https://www.fleetequipmentmag.com/truck-manufacturers-vehicle-connectivity-value-proposition/)), and in 2021 PACCAR partnered with Viaduct to build "comprehensive pictures of individual vehicles" combining connectivity, service, and manufacturing data for OEM-side quality/service prediction — a PACCAR-internal analytics layer, not a dealer- or fleet-facing product ([FreightWaves](https://www.freightwaves.com/news/paccar-partners-with-viaduct-to-enhance-vehicle-uptime)). In 2023 PACCAR also announced a collaboration with Platform Science to embed "Virtual Vehicle," an open OEM telematics platform allowing third-party apps to access real-time vehicle data directly from Kenworth/Peterbilt trucks starting 2024 — this is a genuinely more open in-vehicle data layer than PACCAR Solutions but is a separate, newer initiative ([PR Newswire](https://www.prnewswire.com/news-releases/paccar-and-platform-science-announce-new-collaboration-to-integrate-innovative-virtual-vehicle-solution-in-kenworth-and-peterbilt-trucks-301725837.html)).

## 3. Decisiv SRM — service relationship management

**Confirmed: PACCAR/Peterbilt/Kenworth use Decisiv as their service-event platform.** This is now unambiguous and directly primary-sourced: PACCAR Solutions Service Management is "developed by Decisiv for PACCAR" ([Decisiv — PACCAR Solutions](https://paccar.decisiv.net/)), the login portal lives at `paccar.decisiv.net`, and Decisiv's own marketing states its SRM Ecosystem is used by "most major manufacturers in the industry," manages "nearly 60 percent of commercial vehicles," "more than 74,000 fleet and asset owners," "over 7 million assets," and "more than 14,000 repair events each day" ([Decisiv homepage](https://www.decisiv.com/)).

**What a Decisiv case contains.** A real, published dealer case study (Peterbilt of Atlanta) documents the full case lifecycle: check-in via tablet with driver Q&A and video inspection; QR-code scan capturing VIN and mileage; case creation; diagnostic data, photos, and parts requests attached during the estimate process; warranty-coverage verification; and an estimated completion time routed to the customer for approval ([Decisiv — Peterbilt of Atlanta](https://www.decisiv.com/peterbilt-of-atlanta/)). Decisiv's own help center confirms cases carry line items, invoice totals/numbers, repair status, assets, users, and service-provider records ([PACCAR Solutions support — Cases](https://support.paccar.decisiv.net/hc/en-us/sections/360004692274-Cases)).

**DMS integration — confirmed and dealer-real.** The Peterbilt of Atlanta case shows the case is "immediately exported to Excede [Procede Software's DMS] for pricing, including costs for fleets participating in PACCAR national fleet programs," with items added to the Decisiv case sent to Excede for invoicing, and real-time sync in both directions ([Decisiv — Peterbilt of Atlanta](https://www.decisiv.com/peterbilt-of-atlanta/)). Separately, CDK Global's own Heavy Truck newsletter confirms an equivalent Decisiv↔CDK Drive integration: "This integration will allow users to send line level corrections thru the Decisiv interface and update the DMS appropriately... any story changes in the DMS to be reflected in Decisiv" ([CDK Global Heavy Truck newsletter](https://www2.cdkglobal.com/ht-oem)). Karmak's Fusion DMS documents the same class of PACCAR integration for parts/service/warranty ([Karmak PACCAR Integration](https://www.karmak.com/oem-integrations/paccar)). Note for this specific dealer group: Peterbilt Atlantic runs **CDK Drive**, not Excede — the Decisiv↔CDK Drive path (not the Excede path shown in the Atlanta case study) is the one applicable here.

**Published API / integration programme — confirmed.** Decisiv publishes its own API documentation site (`api-docs.decisiv.net`) describing five APIs: a **Platform API** for "Service Providers and associated dealer systems" covering line items, parts, VMRS codes, notes, attachments, and estimate approval; an **SRM Connect API** for fleets to manage assets and case lifecycle; a **Global Assets API** exposing basic asset info, warranties, recalls, and build information; an **Authentication API**; and a **Service Provider API** exposing customer and customer-asset information ([Decisiv Platform API Specifications](https://api-docs.decisiv.net/)). This is a genuine, documented integration programme, distinct from and more concretely specified than PACCAR's own Connected Truck API catalog. I could not determine from these pages whether the Platform API is available to a third-party developer (like a dealer-owned digital twin) without a Decisiv commercial/sales relationship — the API docs page lists a named sales contact rather than self-serve signup, implying gated access.

## 4. PACCAR Parts systems — ordering, eCommerce, inventory

**Managed Dealer Inventory (MDI).** MDI is PACCAR's daily automated inventory-planning system, launched in North America in 1998: "PACCAR Parts Managed Dealer Inventory Program, or MDI, is one of the most advanced technologies in the supply chain. MDI allows PACCAR Parts to manage each dealer's inventory planning functions and provides visibility to retail transactions. Based on data analysis, parts order recommendations are developed for each dealer location and transmitted electronically to the dealer daily" ([PACCAR Parts Technology page](https://www.paccarparts.com/technology/)). A university thesis on PACCAR Parts Europe's MDI operation (for DAF, PACCAR's European brand) documents the underlying data mechanic precisely: the dealer's DMS generates a nightly "Dealer Inventory File (DIF)" containing sales and inventory data, sent to PACCAR; PACCAR returns a "Suggested Order File (SOF)"; the dealer accepts or overrides it ([TU Eindhoven MDI thesis](https://pure.tue.nl/ws/portalfiles/portal/163151681/Master_Thesis_Jessica_Verhoijsen.pdf)). This is a genuine, standing, one-way-in/one-way-out daily batch data-exchange pattern between dealer DMS and PACCAR — confirmed independently by DMS vendors Karmak (Fusion) and Procede (Excede), both of which describe certified MDI interfaces that push dealer sales/inventory data to PACCAR and pull back stocking recommendations ([Karmak PACCAR Integration](https://www.karmak.com/oem-integrations/paccar); [Procede OEM Integrations](https://www.procedesoftware.com/integrations/)).

**eCommerce / Online Parts Counter (OPC).** OPC is PACCAR Parts' customer/dealer-facing eCommerce platform (Kenworth's storefront is `PartsCounter.Kenworth.com`), offering "24/7/365 ordering access to more than 545,000–1.4 million parts," loyalty-program integration, dealer inventory visibility, and TRP catalog access ([Rihm Kenworth — Online Parts Counter](https://www.rihmkenworth.com/blog/the-benefits-of-online-parts-counter--55573); [PACCAR Parts Customer Service](https://www.paccarparts.com/services/)). CDK Global states OPC integration is "required by PACCAR and available on Fortellis" ([CDK Global Heavy Truck newsletter](https://www2.cdkglobal.com/ht-oem)) — i.e., dealers running CDK Drive must run the OPC integration through the Fortellis marketplace, PACCAR's mandated integration channel.

**Published integration channel — Fortellis.** Fortellis (CDK Global's API marketplace) is the documented mechanism by which third-party developers build certified apps against CDK Drive and connect to OEM systems including PACCAR's. Fortellis publishes a formal developer onboarding process (account creation, API selection, sandbox testing, certification, pilot, cutover) and requires ISV certification before production listing ([Fortellis Docs — The Fortellis Platform](https://docs.fortellis.io/docs/general/ecosystem/introduction/); [CDK Modern API Migration Guide](https://community.fortellis.io/sites/default/files/CDK_Modern.APIs_Migration.Guide_04.14.2023.pdf)). Confirmed live PACCAR integrations on Fortellis: OPC and PRWS (warranty) ([Fortellis blog — Meeting the Unique Needs of Heavy Truck Dealers](https://fortellis.io/blog/meeting-unique-needs-heavy-truck-dealers)). This is directly relevant to Peterbilt Atlantic since it runs CDK Drive.

**What I could not find.** No published PartsPRO-branded system was found under that specific name in PACCAR's own material (the operator's brief names "PartsPRO"; primary PACCAR sources instead consistently use "OPC/Online Parts Counter" for eCommerce and "MDI" for inventory — I could not verify "PartsPRO" as a distinct, currently-branded PACCAR system, and flag this as an absence of evidence rather than a confirmed non-existence).

## 5. PACCAR's enterprise IT posture — SAP, Datasphere, BTP, Business Network

**SAP: confirmed, extensively.** PACCAR is a long-standing, verifiable SAP customer across multiple modules:
- **SAP S/4HANA** — an IBM/Mainline case study states directly: "PACCAR runs their SAP environment on a variety of IBM Power Systems... Last year, PACCAR purchased SAP S/4HANA, an in-memory, relational database" ([Mainline/IBM case study — PACCAR Powers Up for Growth with POWER9 and SAP HANA](https://mainline.com/wp-content/uploads/PDFs/CS_PACCAR-Power.pdf)).
- **SAP IBP** (Integrated Business Planning, advanced planning/scheduling) purchased 2017, live 2017 ([Apps Run The World — PACCAR technographics](https://www.appsruntheworld.com/customers-database/customers/view/paccar-inc-united-states)).
- **SAP HCM Leave Management** purchased 2014 (same source).
- **SAP GTS** (Global Trade Services) — an active PACCAR job posting seeks a "Business Analyst to support the successful implementation of SAP Global Trade Services" ([LinkedIn job posting](https://www.linkedin.com/jobs/view/sap-gts-implementation-business-analyst-at-paccar-4443552439)).
- **SAP Transportation Management (TM)** — multiple current PACCAR job postings for "SAP Transportation Management Functional Analyst" and "Strategic Logistics Planner SAP/TMS Expert" ([TealHQ posting](https://www.tealhq.com/job/sap-transportation-management-functional-analyst_e718dc1b-f6cc-4f3e-ad8e-56d04d2518cd); [BeBee posting](https://bebee.com/us/jobs/strategic-logistics-planner-sap-tms-expert-paccar-bellevue--lensa-7428_af6188c1b61a4f94d50fa72ae0521cffc3c8cc35a23367799f03bd8181576b5a)).
- **SAP/ERP more generally** — accounting and finance job postings across PACCAR corporate and PACCAR India repeatedly list "SAP/ERP system experience desired/preferred" for finance analyst, cost accountant, and accounts payable roles ([Indeed](https://www.indeed.com/q-paccar-sap-jobs.html); [BeBee](https://bebee.com/us/jobs/product-costing-analyst-paccar-columbus--lensa-7428_cc631b154bac401aad3e11e111d52edf83711c722b08cfa84e2d54fbf3dc30a9); [SimplyHired](https://www.simplyhired.co.in/job/8oms98zqpPtkdZVmjTg_zuqvO5eDVqKz3IHrAaEK1UZypy8jnzJttw)).
- **SAP Concur** for travel and expense — a named SAP Concur case study quotes PACCAR's own Global Travel, Expense and Corporate Card manager ([SAP Concur case study — PACCAR](https://www.concur.com/resource-center/casestudy/paccar)).
- **SAP WorkForce Software Analyst** role also posted by PACCAR ([jobs.paccar.com listing](https://jobs.paccar.com/job/Renton-SAP-WorkForce-Software-Analyst-Job-WA-98057/1050855101/)).

**SAP Datasphere / SAP BTP / SAP Business Network — no public evidence found.** I searched PACCAR investor material (10-K filings, annual reports, investor conference material), PACCAR job postings, and SAP's own customer-reference and press channels. PACCAR's 2024 Annual Report discusses its Information Technology Division and PACCAR Connect but makes **no mention of Datasphere, BTP, or Business Network** ([PACCAR 2024 Annual Report](https://www.paccar.com/media/1aml4ipx/2024-annual-report.pdf)). PACCAR's 10-K Information Technology and Cybersecurity section describes reliance on IT systems, some managed by third parties, and telematics/OTA capability, but does not name specific enterprise platforms ([PACCAR Financial Corp 10-K, FY2023, via SEC EDGAR](https://www.sec.gov/Archives/edgar/data/731288/000095017024017921/pcar-20231231.htm)). No SAP customer-reference page, SAP press release, or PACCAR job posting mentioning "Datasphere," "SAP BTP," or "SAP Business Network" was found in this research. **This is an honest gap: absence of evidence, not evidence of absence** — a company running S/4HANA, IBP, GTS, and TM at PACCAR's scale plausibly touches BTP as an underlying platform layer, but no public, citable confirmation exists. This matters directly for the operator's stated goal (Datasphere integration to reach the "PACCAR platform"): there is currently no public indication that PACCAR itself has a Datasphere-based data layer to integrate into. Any Datasphere integration path would necessarily go through PACCAR's public-facing systems (PACCAR Solutions/Decisiv, PACCAR API Catalog, Fortellis) rather than a confirmed PACCAR-side Datasphere environment.

## 6. Dealer obligations to PACCAR — reporting, warranty, sales, parts

**Warranty claim system: PRWS.** PACCAR's warranty system is the **PACCAR Registration and Warranty System (PRWS)**, described by CDK Global as "PACCAR's newest Registration and Warranty system" ([CDK Global Heavy Truck newsletter](https://www2.cdkglobal.com/ht-oem)) and confirmed operationally across dozens of NHTSA-hosted Peterbilt/Kenworth technical and recall bulletins that instruct dealers to "file a claim through PRWS" using specific coding fields.

**Warranty claim data flow and format — well documented.** A claim is built from repair-order (RO) data in the dealer's DMS. NHTSA-hosted bulletins show the exact structured coding schema PACCAR requires in every PRWS claim: **Campaign Code, Campaign Type, Claim Category, Repair Type (Fix-As-Fail / Fix-As-Requested / Proactive), Customer Concern Code, Causal Code, Corrective Action Code, Responsibility Code, Failure Location (a hierarchical part-location code), Causal Part number, Supplier Code, and SRT (Standard Repair Time) Code** — with separate "DWC" (dealer warranty coding) fields for cross-brand repairs ([NHTSA-hosted Peterbilt TSB MC-10185190](https://static.nhtsa.gov/odi/tsbs/2020/MC-10185190-0001.pdf); [NHTSA-hosted Kenworth Powertrain Service Bulletin MC-11034059](https://static.nhtsa.gov/odi/tsbs/2026/MC-11034059-0001.pdf)). Claims come in two forms: "Quick Claims" (pre-defined codes for known campaigns/bulletins) and "long form" claims (manually coded, required for cross-brand repairs, e.g., a Kenworth dealer repairing a Peterbilt chassis) ([NHTSA-hosted TSB MC-10227165](https://static.nhtsa.gov/odi/tsbs/2022/MC-10227165-0001.pdf)). Claims must be filed within a fixed window (commonly 14 days per warranty policy). Dealer DMS vendors (Procede/Excede, Karmak/Fusion, CDK Drive) all publish certified PRWS integrations that auto-populate draft claims from the RO, transmit them, receive real-time PACCAR responses, and allow resubmission — a genuinely dealer-side-automatable but PACCAR-format-mandated flow ([Procede PRWS v1.2 announcement](https://www.linkedin.com/posts/procede-software_procedesoftware-excededms-productupdate-activity-7402395748069548032-qWoj); [Karmak PACCAR Integration](https://www.karmak.com/oem-integrations/paccar)).

**Service Information Record (SIR).** SIR is PACCAR's per-VIN authoritative record of open campaigns/recalls and warranty eligibility; dealers are repeatedly instructed across bulletins to "review SIR for 'Complete' next to the campaign code prior to performing this repair," and PACCAR "will identify and load chassis to PRWS and SIR" for proactive campaigns ([NHTSA-hosted TSB MC-11034059](https://static.nhtsa.gov/odi/tsbs/2026/MC-11034059-0001.pdf); [NHTSA-hosted TSB MC-11020043](https://static.nhtsa.gov/odi/tsbs/2025/MC-11020043-0001.pdf)). SIR sheets are also pullable as PDFs directly from PACCAR via DMS integrations ([Procede PRWS v1.2 announcement](https://www.linkedin.com/posts/procede-software_procedesoftware-excededms-productupdate-activity-7402395748069548032-qWoj)).

**Preventative-maintenance documentation as a warranty precondition — confirmed and dealer-facing.** A live Peterbilt dealer notice (Ohio Peterbilt) states PACCAR's engine warranty explicitly does not cover damage from improper/insufficient maintenance, and as of repair orders opened after November 15, 2024, major-component warranty claims (camshaft, crankshaft, cylinder block/head, connecting rods, gears) require attached preventative-maintenance documentation (receipts, logbooks, ROs) submitted with a Prior Approval request *before* repair begins, or the claim is denied ([Ohio Peterbilt — Warranty Updates](https://ohiopeterbilt.com/pages/warranty-updates)). This is a direct, current, verifiable instance of PACCAR requiring dealer-held operational records (which live only in the dealer's own service history, not in any PACCAR system) as a condition of paying a warranty claim.

**Service reporting/case data.** Every service event that touches PACCAR national fleet programs, warranty, or campaign work flows through a Decisiv case (see §3), which is where PACCAR gets its dealer-side service visibility.

**Parts obligations.** MDI (see §4) constitutes a standing daily reporting obligation: dealers' DMS must generate and transmit a daily inventory/sales data file to PACCAR in order to receive stocking recommendations, and OPC integration is stated by CDK Global to be "required by PACCAR" for CDK Drive dealers ([CDK Global Heavy Truck newsletter](https://www2.cdkglobal.com/ht-oem)).

**Sales reporting.** I found no PACCAR-specific published document describing a dealer sales-reporting data schema or cadence (distinct from state DMV dealer-licensing sales reporting, which is a legal, not OEM, obligation and out of scope here). This is a gap: PACCAR almost certainly receives sales/registration data as part of new-truck delivery and warranty registration (registration is literally in "PRWS" — Registration and Warranty System — implying vehicle registration data flows to PACCAR at point of sale), but no primary PACCAR document spelling out a discrete "sales reporting" obligation or format was located.

## 7. The last-mile gap — what the PACCAR platform does not capture

Based strictly on the evidence above, the following dealership-operational realities are **not** captured anywhere in PACCAR Solutions, SmartLINQ/TruckTech+, Decisiv, PACCAR Parts, or PRWS:

- **Full shop-floor operations beyond the Decisiv case shell.** Decisiv captures check-in, diagnostics/photos/parts requests, and estimate/approval status, but the underlying technician labor detail, shop scheduling, bay/stall assignment, technician productivity, and job-costing detail live in the dealer's own DMS (CDK Drive here), not in Decisiv or PACCAR Solutions — Decisiv exports *to* the DMS for pricing/invoicing, it does not host the dealer's full operational record ([Decisiv — Peterbilt of Atlanta](https://www.decisiv.com/peterbilt-of-atlanta/)).
- **Non-warranty, non-campaign service history.** The evidence shows PACCAR systems are structured around warranty/campaign claims (PRWS) and PACCAR national fleet program service events (Decisiv). Customer-pay repair orders with no warranty or campaign component, and the dealer's full accounting/financial record of those jobs, are not shown anywhere in the PACCAR-side material reviewed.
- **Preventative-maintenance and service records as evidentiary documents.** PACCAR's own warranty policy (§6) requires the *dealer* to produce and hold PM documentation — proof that PACCAR's own systems do not already contain this record. If PACCAR held it, it would not need to demand it as a Prior Approval attachment.
- **Sales/CRM/customer relationship data.** No PACCAR system reviewed captures dealer-side sales pipeline, customer relationship history, financing, or trade-in data — this is DMS/CRM territory, untouched by PACCAR Solutions, Decisiv, or PRWS.
- **Parts counter retail transactions not tied to MDI-relevant SKUs, or to non-PACCAR parts lines.** MDI's daily file exchange is about *inventory replenishment* signal, not a full transactional ledger; OPC covers PACCAR/TRP and select non-PACCAR parts ordering but is an ordering front-end, not the dealer's own parts financial system.
- **Raw telemetry.** As established in §2, dealers and fleets see PACCAR's processed/interpreted fault output, not the raw CAN-bus or J1939 event stream — the "translation" happens inside PACCAR's back office before anything reaches a portal.
- **Cross-franchise, cross-DMS operational data.** Since Peterbilt Atlantic runs CDK Drive for heavy truck and the group's separate BRP powersports franchise (Extreme Torque Motorsports) runs LightspeedDMS, nothing in the PACCAR platform stack (which is single-OEM, single-DMS-vendor-integration by design) has any mechanism to unify data across those two lines of business — that unification is structurally outside PACCAR's platform scope, by definition, since PACCAR has no relationship with BRP or Lightspeed.
- **A PACCAR-side Datasphere/BTP data layer to integrate into.** As found in §5, no such layer is publicly confirmed to exist yet; the "last mile" for a Datasphere-based dealer twin, at least as of this research, has no PACCAR-side Datasphere endpoint to extend into — the practical integration points, per the evidence gathered, are the licensed PACCAR API Catalog, Decisiv's own APIs, and Fortellis-brokered DMS integrations (OPC, PRWS, Decisiv sync).
