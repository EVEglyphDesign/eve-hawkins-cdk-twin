# Lane D — SAP Datasphere as the Destination: What Must the Dealer-Side Twin Emit?

## What I found and what I didn't (five-line summary)

SAP Datasphere still exists as a product name in 2026 but is no longer independently sellable — as of January 1, 2026 it was removed from new BTP/CPEA/PAYG price lists and folded into **SAP Business Data Cloud (BDC)**, a SaaS bundle announced February 2025 with Databricks as a first-party service ([SAP News](https://news.sap.com/2025/02/sap-databricks-open-bold-new-era-data-ai/), [SAP Community](https://community.sap.com/t5/technology-blog-posts-by-sap/announcement-sap-datasphere-and-sap-analytics-cloud-availability-via-sap/ba-p/14140920)); existing tenants are preserved but future procurement runs through BDC. There is no SAP-built dealer or heavy-truck data model to conform to — the only SAP automotive content is OEM/supply-chain facing (Datasphere's "Automotive (AUT)" package covers Sales/Purchasing/Production Order data from S/4HANA, not dealership floor data) ([help.sap.com AUT package](https://help.sap.com/docs/SAP_DATASPHERE/cb7a0296feb849089b00d461168e3e69/3263c997716210148212b18947049c44.html)), and SAP's actual dealer-management product (DBM, IS-A-DBM) is a legacy on-premise ERP add-on last documented in 2016, not a Datasphere-native model ([help.sap.com DBM](https://help.sap.com/docs/SAP_DEALER_BUSINESS_MANAGEMENT/54c1b516c0fa4eb7a893ff13dcf76e7d/1378c2e8692e41da9384b03c2e861522.html)). Inbound paths are real and multiple — Open SQL schema/database users (ODBC write), Replication Flows, Data Flows, Cloud Connector for on-prem, and native Parquet/CSV/JSON/ORC file ingestion via S3, Azure Blob/ADLS Gen2, and Google Cloud Storage connections are all documented, with Parquet and CSV as the two formats explicitly supported end-to-end ([help.sap.com Working with Connections](https://help.sap.com/docs/SAP_DATASPHERE/be5967d099974c69b77f4549425ca4c0/eb85e157ab654152bd68a8714036e463.html), [help.sap.com Generic SFTP formats](https://help.sap.com/docs/SAP_DATASPHERE/be5967d099974c69b77f4549425ca4c0/b645de78a8374c24871ab6169be40d35.html)). Licensing is consumption-based Capacity Units with no published minimum tenant size, but Premium Outbound Integration is priced in punitive small blocks (500 Capacity Units per 20GB for the first 10 blocks) that makes any data-egress-heavy architecture expensive at small scale ([SAP BDC Service Description Guide](https://assets.cdn.sap.com/agreements/product-use-and-support-terms/service-description-guides/sap-business-data-cloud-service-description-guide-english-v7-2026.pdf)). What I could not find: any public per-tenant subscription minimum/floor price, any confirmation that a mid-size dealer group has its own standalone Datasphere tenant in production, and any SAP documentation describing a supported architecture for a *third-party partner* writing directly into a *customer-owned* Datasphere tenant as a matter of course (cross-tenant sharing exists only via Data Marketplace/data products and content transport, not live cross-tenant space access) ([SAP Community: cross-tenant](https://community.sap.com/t5/technology-q-a/can-i-connect-from-one-datasphere-tenant-directly-to-another-to-access/qaq-p/12779567)).

## 1. What SAP Datasphere is in 2026

SAP Datasphere was launched in March 2023 as the evolution of SAP Data Warehouse Cloud, combining data integration, cataloging, semantic modeling, data warehousing, and virtualization into one service on SAP Business Technology Platform (BTP) ([help.sap.com Big Picture](https://help.sap.com/docs/sap-btp-guidance-framework/integration-architecture-guide/big-picture-of-available-sap-components-and-solutions-b7fb780035164122ba49b1ca969a4d22)).

In February 2025 SAP announced **SAP Business Data Cloud (BDC)**, a "fully managed SaaS solution" that unifies SAP Datasphere, SAP Analytics Cloud, and SAP Business Warehouse, and includes **SAP Databricks as a first-party data service** via a "landmark partnership" with Databricks ([SAP News, Feb 2025](https://news.sap.com/2025/02/sap-databricks-open-bold-new-era-data-ai/)). Per that announcement, Datasphere's capabilities "remain fully supported" and are "natively available" inside BDC, using Delta Sharing to harmonize SAP data with lakehouses bi-directionally in a "zero-copy" model.

The commercial cutover happened on schedule: an SAP Community announcement (July 2025) stated Datasphere and SAP Analytics Cloud would be **removed from the list of Eligible Cloud Services for new BTPEA, CPEA, and PAYG subscriptions as of January 1, 2026** — new customers can no longer buy standalone Datasphere; existing contracts run out and then must move to BDC, though "no technical migration" is required because tenants are preserved as-is ([SAP Community announcement](https://community.sap.com/t5/technology-blog-posts-by-sap/announcement-sap-datasphere-and-sap-analytics-cloud-availability-via-sap/ba-p/14140920)). SAP's own support knowledge base confirms Datasphere shows as a **deprecated service in BTP as of December 31, 2025** ([SAP Support KBA 3630656](https://userapps.support.sap.com/sap/support/knowledge/en/3630656)), and third-party reporting (credible but not primary) states Datasphere and SAC were "officially deprecated as of 12/31/2025" and removed from the BTP service list on 1/2/2026, with SAP calling the move a "rewire" rather than a migration ([LinkedIn, Matthew Reddy, Jan 2026](https://www.linkedin.com/posts/matthewreddy_in-case-there-were-still-questions-as-to-activity-7421903582066618368-To56)) — *this LinkedIn characterization is corroborating, not primary, evidence, but it is consistent with the SAP-published KBA above.*

**Bottom line as of mid-2026:** "SAP Datasphere" as a name and as a working system still exists and is still the thing that customers configure, model in, and connect data to. But as a commercial SKU it is being absorbed into SAP Business Data Cloud, and it is explicitly billed by SAP itself as "the sanctioned semantic layer between SAP source systems and BDC" rather than a permanent standalone destination ([LinkedIn, Ronald Konijnenburg, May 2026](https://www.linkedin.com/posts/ronaldkonijnenburg_bdc-icebergrightahead-datasphere-activity-7457154250305855488-21ze) — *inference from a credible secondary analyst, not an SAP primary statement, flagged as such*). SAP's own current product page (July 2026) frames Datasphere as "a key component in SAP Business Data Cloud, serving as the knowledge core that unifies semantics, data products, and modeling" ([sap.com/products/data-cloud/datasphere.html](https://www.sap.com/products/data-cloud/datasphere.html)) — this is the primary-source confirmation that Datasphere is subordinate to, not separate from, BDC going forward.

Underlying storage architecture is also in flux. According to a detailed, well-sourced (but non-SAP, LinkedIn) analysis referencing SAP's May 2026 Dremio acquisition: BDC today lands SAP-managed data products in **HANA Data Lake Files (HDLF) as Delta tables**, using **Delta Sharing** as the zero-copy interoperability protocol with Databricks; the same source states BDC is moving toward being **"Iceberg-native with Polaris as catalog,"** with Delta Lake being "demoted to a compatibility layer" — this is **inference/informed speculation from a third party**, not an SAP statement, and is flagged as such ([LinkedIn, Ronald Konijnenburg](https://www.linkedin.com/posts/ronaldkonijnenburg_bdc-icebergrightahead-datasphere-activity-7457154250305855488-21ze)). Independent corroboration exists that Datasphere's File Object Store (FOS) already uses **Apache Iceberg architecture with Parquet files** for lakehouse-style workloads, distinct from HANA Data Lake Files proper, which stores files in object storage without Iceberg table structure ([LinkedIn technical explainer](https://www.linkedin.com/pulse/decoding-saps-modern-data-storage-hana-lake-iceberg-krishnan-ckpue) — again secondary, flagged).

## 2. Inbound integration paths and their real constraints

| Path | What it actually does | Constraints (primary-sourced) |
|---|---|---|
| **Open SQL schema / database users** | A Space Administrator creates a database user with an Open SQL schema attached to the space. The external system connects via **ODBC** to the run-time SAP HANA Cloud database, can create tables/views and **write data into the schema**, and can read data the space exposes ([help.sap.com](https://help.sap.com/docs/SAP_DATASPHERE/be5967d099974c69b77f4549425ca4c0/3de55a78a4614deda589633baea28645.html?locale=en-US)). | Access method is explicitly **ODBC**; JDBC is not mentioned on the page. Requires Space Administrator role to provision. Usage is metered: the contractual service guide caps the **OpenSQL interface at 1 GB of network data transfer per 1 GB of compute memory, per tenant, per month**, with SAP reserving the right to bill overage ([SAP BDC Service Description Guide](https://assets.cdn.sap.com/agreements/product-use-and-support-terms/service-description-guides/sap-business-data-cloud-service-description-guide-english-v7-2026.pdf)). |
| **Replication Flows** | Move data from a source connection to a target (including into Datasphere local tables) with three load types: Initial Only, Initial and Delta, Delta Only. Source connection compatibility varies: **ABAP sources, Microsoft SQL Server, and SAP HANA support all three load types**; **Confluent Kafka and Cloud Storage Provider connections support only Initial-and-Delta**; **local file tables support none of the delta modes** ([help.sap.com Load Types and Connections](https://help.sap.com/docs/SAP_DATASPHERE/c8a54ee704e94e15926551293243fd1d/10891192186c4920b08939a7b46adc79.html)). | Not every source/target pairing supports every load type — this must be checked per connector before assuming true CDC-style replication is possible. Community reporting confirms **Replication Flows do not currently support `.parquet` files on Azure Data Lake Gen2**, only `.csv` — a real, documented gap ([SAP Community Q&A](https://community.sap.com/t5/technology-q-a/how-to-use-azure-data-lake-gen2-parquet-files-as-source-for-sap-datasphere/qaq-p/14293169)). |
| **Data Flows** | A separate mechanism (built on Apache Spark) for transformation-heavy loads; unlike Replication Flows, **Data Flows do support `.parquet` and `.csv` files on Azure Data Lake Gen2** per the same community thread. Supported file types for flow-based ingestion generally include **CSV, JSON, JSONLines, and Parquet** (Parquet is described as the default), with optional Gzip/Snappy compression and an "Apache Spark Compatibility" toggle for Parquet time columns ([help.sap.com General Information](https://help.sap.com/docs/SAP_DATASPHERE/c8a54ee704e94e15926551293243fd1d/5a14eb1709a24a35821d1618285d021d.html)). | Choice between Replication Flow and Data Flow is not just stylistic — it is dictated by which file format and load type you need, per the same community source. |
| **Premium Outbound Integration** | A metered, block-priced service for exporting data **out** of Datasphere at volume. | Per the SAP Business Data Cloud Service Description Guide (v7-2026): priced in **blocks of 20GB**, at **500 Capacity Units for each of the first 10 blocks**, dropping to 350 (next 15), 200 (next 25), 100 (next 50), and 35 (9999+ blocks) ([SAP BDC Service Description Guide](https://assets.cdn.sap.com/agreements/product-use-and-support-terms/service-description-guides/sap-business-data-cloud-service-description-guide-english-v7-2026.pdf)). This is steeply front-loaded — small, occasional outbound volumes are disproportionately expensive per GB compared to bulk/steady-state usage. Third-party reporting (not primary) states SAP cut Premium Outbound pricing by 50% at some point and that the calculation is based on **uncompressed data volume**, with each cell's contribution depending on data type ([Expertum](https://expertum.net/premium-outbound-integration-in-sap-datasphere/) — flagged as secondary/vendor-blog, used only as corroborating color, not as the primary cost figure, which comes from the SAP PDF itself). |
| **Object store / data lake ingestion (S3, Azure, GCS)** | Datasphere has native, predefined connection types for **Amazon S3**, **Google Cloud Storage**, **Microsoft Azure Blob Storage**, and **Microsoft Azure Data Lake Store Gen2** ([help.sap.com Connection Definition File Formats index](https://help.sap.com/docs/SAP_DATASPHERE/d0ecd6f297ac40249072a44df0549c1a/49e8be9a723c4abf842aaab6810ebf2c.html), [Google Cloud Storage Connections](https://help.sap.com/docs/SAP_DATASPHERE/be5967d099974c69b77f4549425ca4c0/aec242c29188408c9ebe1a3ab63ce28b.html), [Azure Blob Storage Connections](https://help.sap.com/docs/SAP_DATASPHERE/be5967d099974c69b77f4549425ca4c0/df5a7c56ac21472c973f6fab341f3991.html)). Supported file formats via SFTP/object-store paths: **JSON, JSONL, CSV, XLS, XLSX, ORC, and Parquet** ([help.sap.com Generic SFTP Connections](https://help.sap.com/docs/SAP_DATASPHERE/be5967d099974c69b77f4549425ca4c0/b645de78a8374c24871ab6169be40d35.html)). A local table can also be created directly from CSV file upload in the Data Builder, capped at **25MB** and Unicode-text-only ([SAP-docs GitHub mirror](https://github.com/SAP-docs/sap-datasphere/blob/main/docs/Acquiring-Preparing-Modeling-Data/Acquiring-and-Preparing-Data-in-the-Data-Builder/creating-a-local-table-from-a-csv-file-8bba251.md)). | As noted above, format support is **feature-dependent, not connection-type-blanket**: Replication Flows and Data Flows differ in which formats/load-types they accept on the same storage connection. The object store within Datasphere itself ("File Object Store") is described by a secondary source as using **Apache Iceberg architecture with Parquet files**, distinct from raw HANA Data Lake Files object storage ([LinkedIn technical explainer](https://www.linkedin.com/pulse/decoding-saps-modern-data-storage-hana-lake-iceberg-krishnan-ckpue) — flagged as secondary). |
| **Delta Sharing / Databricks interoperability** | SAP's own Feb 2025 announcement states BDC "uses native capabilities like Delta Sharing to harmonize SAP data products with existing lakehouses bi-directionally" in a "zero-copy approach," and that on-prem BW customers get "native integration" to "access data as a data product with the object store via Delta Share" ([SAP News](https://news.sap.com/2025/02/sap-databricks-open-bold-new-era-data-ai/)). SAP's contractual guide separately lists metered "SAP Business Data Cloud Connect for Databricks" capacity services (Inter-Region Data Transfer, Processing Requests) as distinct billable line items ([SAP BDC Service Description Guide](https://assets.cdn.sap.com/agreements/product-use-and-support-terms/service-description-guides/sap-business-data-cloud-service-description-guide-english-v7-2026.pdf)). | This is a BDC-level (not classic-Datasphere-tenant-level) capability tied to the SAP Databricks first-party service; it is not the same thing as a generic external Databricks workspace reading Datasphere tables for free — it is a metered "Connect" product with its own capacity units. |
| **OData and REST-based ingestion; Datasphere APIs** | Datasphere exposes data outward via **public OData APIs** for consumption by Excel, Power BI, and other clients (explicitly stated in the "Getting Started" documentation: "Seamless integration with SAP Analytics Cloud, Microsoft Excel, and public OData APIs to support consumption by other clients, tools, and apps") ([help.sap.com Getting Started](https://help.sap.com/docs/SAP_DATASPHERE/d4f3c5a0bb074d09ae9b42b2b9bd7a08/5db9a099826c467e93ff0994fc185589.html)). A **command-line interface (`@sap/datasphere-cli`)** exists as an npm Node.js package for interacting with a Datasphere tenant from the terminal ([help.sap.com CLI install](https://help.sap.com/docs/SAP_DATASPHERE/d0ecd6f297ac40249072a44df0549c1a/f7d5eddf20a34a1aa48d8e2c68a44e28.html), [npm package](https://www.npmjs.com/package/@sap/datasphere-cli)). | OData API usage is metered: the SAP BDC contract caps usage at **2,000 OData API Calls per 1 GB of compute memory, per tenant, per month**, with overage billable ([SAP BDC Service Description Guide](https://assets.cdn.sap.com/agreements/product-use-and-support-terms/service-description-guides/sap-business-data-cloud-service-description-guide-english-v7-2026.pdf)). The CLI's documented scope, per its own install page, is limited to "interact with your SAP Datasphere tenant from the command line" — the install page does not itself describe CSN import/export, catalog operations, or content deployment; those capabilities are referenced elsewhere in SAP's docs (e.g., the Content Network / Transport application) but not confirmed as CLI subcommands from the page fetched. |
| **Cloud Connector for on-premise/private sources** | Explicitly required as "a link between SAP Datasphere and your on-premise sources" for: **Data Flows, Replication Flows**, model import from SAP BW/4HANA and SAP S/4HANA On-Premise (via a live "tunnel" type connection), and remote tables from SAP HANA on-premise via SAP HANA Smart Data Access ([help.sap.com Cloud Connector context](https://help.sap.com/docs/SAP_DATASPHERE/9f804b8efa8043539289f42f372c4862/35141e7668774958b5e59495f7a7828e.html)). | Setup requires installing Cloud Connector inside the on-premise network, holding subaccount information, and configuring it before any connection to an on-prem source will work — this is a real infrastructure and firewall/network dependency, not a pure SaaS-to-SaaS integration. For a dealer twin, this matters only if the twin itself is hosted on-premise rather than in a cloud tenant the operator controls. |

## 3. What SAP Datasphere expects semantically

Datasphere's internal modeling stack is built around **CSN — Core Schema Notation** ("pronounced 'Season'"), described by SAP's own open GitHub Pages specification as "a JSON-based serialization format for Core Data Services (CDS) models" used to describe "domain, data and service models... on a conceptual level, with rich semantics and annotations," and explicitly scoped for "cross-technology integration (CAP, ABAP, Datasphere, etc.)" ([sap.github.io/csn-interop-specification](https://sap.github.io/csn-interop-specification/)). This specification page is a primary SAP source (hosted under the `sap` GitHub organization) but does **not state its own license** or explicitly confirm open-source status on the page content retrieved — that is a gap, not an assumption filled in.

On top of the raw table/view layer, Datasphere's own "Getting Started" documentation describes a layered modeling approach: graphical/SQL data flow editors for the raw **Data Layer**, and a separate **Business Builder** for the **Business Layer**, where "multi-dimensional modeling with powerful analytical capabilities" happens, along with **Analytic Models** ([help.sap.com Getting Started](https://help.sap.com/docs/SAP_DATASPHERE/d4f3c5a0bb074d09ae9b42b2b9bd7a08/5db9a099826c467e93ff0994fc185589.html)). SAP Community's own technical blog series confirms the fact/dimension pattern explicitly: "the business layer of SAP Datasphere allows you to model these facts independently and then bring them together" via a "multi-fact" pattern analogous to Business Warehouse's Multi-Provider concept — i.e., independently modeled fact tables joined to shared conformed dimensions ([SAP Community, Analytic Model Series Blog #10](https://community.sap.com/t5/technology-blog-posts-by-sap/sap-datasphere-analytic-model-series-blog-post-10-design-multi-fact-in/ba-p/13551770)).

**What a dealer data model would need to look like to be consumable, based on this evidence:**
- Data lands first as **tables/views** in a space (via Open SQL schema writes, Replication Flows, Data Flows, or file import), in a raw/staging structure.
- To be usable analytically inside Datasphere's own tooling (not just passed through), that raw data needs to be organized into a **star-schema-like pattern**: fact tables (e.g., repair orders, parts transactions, vehicle sales) associated with shared, reusable **dimension tables** (customer, vehicle/unit, technician, location, time) in the Business Layer, then exposed as **Analytic Models**.
- For cross-system semantic interoperability (e.g., exchanging metadata with CAP or ABAP-based systems, or with SAP's own content network), models should ideally be expressible in **CSN JSON** — this is the format SAP itself uses to describe entities, associations, types and annotations across its ecosystem.
- **Gap/inference flagged:** I found no SAP documentation stating that Datasphere *requires* incoming raw data to already be in CSN form — CSN appears to be the format Datasphere's own modeling layer emits/consumes for content transport and cross-tool exchange (see the CLI, Content Network, and cross-tenant transport findings in Section 4), not a mandatory input contract for every data flow. Raw CSV/Parquet ingestion followed by in-tool modeling is the documented normal path.

## 4. Licensing and cost model

SAP Datasphere/BDC billing runs on **Capacity Units (CUs)** consumed per month, based on metered usage across dozens of discrete "Capacity Services" (compute, storage, integration, catalog, etc.), each with its own Capacity Unit of Measure and Capacity Unit Value; **unused Capacity Units do not carry over** month to month, and usage is **not prorated** for partial months ([SAP Business Data Cloud Service Description Guide, v7-2026](https://assets.cdn.sap.com/agreements/product-use-and-support-terms/service-description-guides/sap-business-data-cloud-service-description-guide-english-v7-2026.pdf), Attachment A).

Representative Capacity Unit Values from the official contract document (per the stated Capacity Unit of Measure):
- **Datasphere SaaS Foundation**: 0.926 CU per tenant-hour
- **Disk Storage**: 0.004 CU per 16GB-storage-hour
- **Catalog Storage** (512MB included/month): 1.096 CU per GB-storage-hour
- **Data Integration** (200 hours included/month): 0.784 CU per 5GB-memory-hour
- **Object Store**: 0.103 CU per 1TB-storage-hour
- **Premium Outbound Integration**: 500 CU/block for the first 10 blocks of 20GB, tapering to 35 CU/block beyond 9,999 blocks

There is **16GB of Catalog Storage included per month** as part of the SAP Business Data Cloud, core capacity Cloud Service ([SAP BDC Service Description Guide](https://assets.cdn.sap.com/agreements/product-use-and-support-terms/service-description-guides/sap-business-data-cloud-service-description-guide-english-v7-2026.pdf)). No document found states a minimum number of Capacity Units, a minimum monthly spend floor, or a minimum tenant-size requirement specific to standing up a bare SAP Datasphere/BDC tenant — the contract lists minimum-subscription *linkage* requirements only for specific **Intelligent Packages** (e.g., Finance Intelligence requires an existing SAP Finance/S4 subscription of equal or greater size), none of which apply to a dealer group with no existing SAP ERP footprint.

**Could a mid-size dealer group plausibly hold its own tenant?** No document found confirms or denies this directly for a company of Hawkins Group's scale. What is confirmed: (a) tenant provisioning is per-organization/self-service in principle (Data Marketplace and Data Sharing Cockpit availability is gated only by tenant provisioning date, not company size — "only available in SAP Datasphere tenants provisioned since January 25, 2021," per the SAP-docs GitHub mirror of the official docs) ([SAP-docs GitHub](https://github.com/SAP-docs/sap-datasphere/blob/main/docs/Acquiring-Preparing-Modeling-Data/purchasing-data-from-data-marketplace-4096fb8.md)); (b) cost is consumption-based rather than seat-based, so a small, low-volume tenant is technically possible but the **Premium Outbound Integration pricing curve punishes small/occasional egress volumes disproportionately** (500 CU per 20GB in the first tier is a very high per-GB rate compared to bulk tiers) — this makes a low-volume, sporadic-egress dealer tenant economically inefficient relative to a high-volume enterprise tenant, though not technically prohibited. This is **inference**, not a documented SAP statement about dealer-group viability specifically.

**Can a partner integrate into someone else's tenant?** The evidence here is fairly clear and somewhat restrictive:
- **No live cross-tenant data blending or space sharing exists.** SAP Community (a customer/MVP answering a peer question, not SAP itself, but corroborated by the CSN/content-transport mechanics referenced) states plainly: **"It's not possible to share spaces between tenants... you're missing a lot of things this way"** when trying to connect one Datasphere tenant directly to another; the workaround is treating an exposed view as a **remote table via HANA Smart Data Access**, which loses all semantic modeling (associations, hierarchies) and arrives as a "PLAIN table" ([SAP Community Q&A](https://community.sap.com/t5/technology-q-a/can-i-connect-from-one-datasphere-tenant-directly-to-another-to-access/qaq-p/12779567)).
- SAP's own documentation confirms cross-tenant content movement is handled through the **Content Network / Transport application**, requiring a **DW Administrator** global role (or scoped Space Administrator with Lifecycle privilege), moving packages via a private cloud storage zone, and requiring **matching space and connection names** between source and target tenants ([help.sap.com Transporting Content Between Tenants](https://help.sap.com/docs/SAP_DATASPHERE/be5967d099974c69b77f4549425ca4c0/df12666cf98e41248ef2251c564b0166.html), [SAP Support KBA 3527253](https://userapps.support.sap.com/sap/support/knowledge/en/3527253)).
- The **Data Marketplace / Data Sharing Cockpit** is the documented, SAP-sanctioned mechanism for cross-organization data exchange: a data provider creates a "Data Provider" profile (requires the "Spaces (Update)" privilege), publishes data as licensed "data products" (free or paid, one-time or refreshed), and a consumer in a different tenant "joins" a context to receive it ([SAP Community how-to thread](https://community.sap.com/t5/technology-blog-posts-by-sap/new-video-series-for-sap-datasphere-data-marketplace/bc-p/14265202/highlight/true), [help.sap.com Data Provider guide](https://help.sap.com/docs/SAP_DATASPHERE/e4059f908d16406492956e5dbcf142dc/e479b7b4c95741c7a7a1d42397984c7e.html)). This is licensing-and-publish, not a partner writing operationally into a customer's live tenant.
- **SAP Analytics Cloud live connections can span Datasphere tenants** for reporting purposes only — "any SAP Datasphere system can be connected to any SAC system via the SAP Datasphere live connection," but **blending data across Datasphere tenants is explicitly unsupported** ([SAP Community, Oct 2025](https://community.sap.com/t5/technology-blog-posts-by-members/unsupported-features-with-sap-datasphere-live-connections-in-sap-analytics/ba-p/14228053)).

**Practical reading for this project (inference, flagged):** if PACCAR or SAP builds/hosts the Datasphere tenant, the dealer twin (EVEglyph/Hawkins side) would most plausibly act as a **Data Marketplace provider or a Replication/Data-Flow source feeding into PACCAR's tenant**, rather than a co-tenant with live write access to shared spaces — the documented architecture does not support the latter.

## 5. SAP automotive/dealer content packs

Two distinct things exist under the SAP "automotive" umbrella, and neither is a ready-made dealer/twin schema:

1. **SAP Datasphere Automotive (AUT) content package** — a pre-built content pack inside Datasphere's Content Network, explicitly scoped to **"Responsive Supply Networks" for the automotive sector**, sourced from **SAP S/4HANA systems**, and covering **Sales Order, Purchasing Order, and Production Order Data** as "a foundation for future expansions" ([help.sap.com Automotive (AUT)](https://help.sap.com/docs/SAP_DATASPHERE/cb7a0296feb849089b00d461168e3e69/3263c997716210148212b18947049c44.html)). This is **OEM/manufacturer-and-supply-chain facing**, not dealer-facing — nothing in the retrieved page mentions dealer, retail, service, or parts-counter entities. It requires an existing S/4HANA source; a dealer group running CDK Drive or LightspeedDMS has no S/4HANA system to source from.

2. **SAP Dealer Business Management (DBM / IS-A-DBM)** — SAP's actual dealer-facing product, but it is a classic on-premise ERP add-on (part of the older "SAP for Automotive" industry package, first released 2005), **not a Datasphere-native model**. The most recent version documentation found is **DBM 8.1 SP01, dated February 2016**, built on SAP ERP 617 / NetWeaver 7.4 SP10 ([help.sap.com DBM overview](https://help.sap.com/docs/SAP_DEALER_BUSINESS_MANAGEMENT/54c1b516c0fa4eb7a893ff13dcf76e7d/1378c2e8692e41da9384b03c2e861522.html)). It covers vehicle sales (new/used), service, parts management, warranty claims, and multi-brand/multi-location dealer organizations, integrated with SAP MM, SD, FI, CO ([help.sap.com DBM](https://help.sap.com/docs/SAP_DEALER_BUSINESS_MANAGEMENT/54c1b516c0fa4eb7a893ff13dcf76e7d/1378c2e8692e41da9384b03c2e861522.html)). No evidence was found of a current release, a cloud/Datasphere port, or ongoing active development beyond the 2016 documentation — this reads as a **legacy product**, not a live foundation to build a 2026 twin on. Secondary sources (Hicron, TAdviser — SAP partner/consultancy sites, not primary) describe it as still deployable and integratable via interfaces with OEM systems, but provide no version currency past what SAP's own help portal shows.

3. **SAP Industry Network for Automotive** — SAP's current (2026) automotive industry offering is described on SAP's own site as "a range of packages that address the specific needs of companies in the automotive sector — from sustainability management through demand planning and supply chain visibility" ([sap.com Industry Network for Automotive](https://www.sap.com/industries/automotive/industry-network-automotive.html)). Nothing in the retrieved snippet references dealer, retail, or aftersales/service-bay entities — it reads as supply-chain-collaboration tooling between OEMs and suppliers, not a dealer content model.

4. **Real-world precedent for heavy truck + Datasphere**: **MAN**, a genuine heavy-commercial-vehicle OEM (directly comparable in kind to PACCAR), is an SAP customer reference for Datasphere — SAP's own case study states MAN uses Datasphere for "a dynamic approach of harmonized data" with SAP Analytics Cloud for reporting and planning ([sap.com MAN case study](https://www.sap.com/assetdetail/2024/10/5ee834a8-da7e-0010-bca6-c68f7e60039b.html)). However, the retrieved case-study page does **not** name specific data domains and does **not** mention dealer network data at all — it confirms Datasphere is viable for heavy-truck OEM data harmonization in principle, but gives no evidence it extends to or includes dealer-side operational data.

**Finding, stated plainly per the rules: no open or SAP-native dealer/DMS entity model exists that a dealer-side twin could conform to today.** The Automotive (AUT) content pack is OEM-supply-chain scoped and requires S/4HANA; DBM is a 2016-vintage on-premise ERP module with no confirmed Datasphere presence; the Industry Network for Automotive is inter-OEM/supplier collaboration tooling. The dealer twin would have to define its own entity model and either express it as CSN or land it as tables/views and rebuild the semantic layer inside Datasphere's Business Builder from scratch.

## 6. The realistic alternative: landing the twin in open formats first

The evidence strongly supports that **Parquet is the best-supported open file format** for later bridging into Datasphere, with CSV a close second, and native Iceberg/Delta table-format ingestion being more indirect:

- **Parquet is explicitly Datasphere's default output format** for replication and is read/write-capable across the Generic SFTP connection type, alongside JSON, JSONL, ORC, and CSV ([help.sap.com Generic SFTP Connections](https://help.sap.com/docs/SAP_DATASPHERE/be5967d099974c69b77f4549425ca4c0/b645de78a8374c24871ab6169be40d35.html), [help.sap.com General Information / replication flow target settings](https://help.sap.com/docs/SAP_DATASPHERE/c8a54ee704e94e15926551293243fd1d/5a14eb1709a24a35821d1618285d021d.html)).
- **CSV is universally accepted** as a direct file-upload source into the Data Builder (25MB cap, Unicode text only) and across Replication Flows, Data Flows, and object-store connections ([SAP-docs GitHub CSV import](https://github.com/SAP-docs/sap-datasphere/blob/main/docs/Acquiring-Preparing-Modeling-Data/Acquiring-and-Preparing-Data-in-the-Data-Builder/creating-a-local-table-from-a-csv-file-8bba251.md)).
- **Parquet on Azure Data Lake Gen2 is only supported through Data Flows, not Replication Flows**, per a specific, dated (Dec 2025) SAP Community troubleshooting thread — a real and current gap that any Parquet-first architecture would need to route around by using Data Flows or by first landing as CSV ([SAP Community](https://community.sap.com/t5/technology-q-a/how-to-use-azure-data-lake-gen2-parquet-files-as-source-for-sap-datasphere/qaq-p/14293169)).
- **Apache Iceberg and Delta Lake tables are not directly listed as native "connection types"** for inbound ingestion in any Datasphere connection documentation retrieved. Instead: (a) SAP HANA Cloud's underlying database layer supports `IMPORT FROM PARQUET FILE IN DELTA LAKE` and `IN HIVE PARTITION` SQL statements for reading Delta-Lake-organized or Hive-partitioned Parquet directories directly via SQL ([help.sap.com HANA Cloud Parquet support](https://help.sap.com/docs/hana-cloud-database/sap-hana-cloud-sap-hana-database-administration-guide/support-for-open-source-formats?locale=en-US&version=latest)) — this is a HANA Cloud database capability, and its applicability inside a standard Datasphere space (versus a raw HANA Cloud instance) was not independently confirmed in the sources retrieved; (b) community members report a real-world workaround of writing Parquet out via an outbound replication flow to an Azure Data Lake, then having a separate lake process convert the Parquet into Iceberg for downstream reporting tools — i.e., Iceberg interoperability today is achieved by external tooling around Datasphere, not a native Datasphere-side Iceberg reader ([SAP Community Q&A on Iceberg reporting](https://community.sap.com/t5/technology-q-a/approaches-for-reporting-on-datasphere-data-through-iceberg-table-format-in/qaq-p/14157605)).
- **Delta Sharing is the sanctioned zero-copy interoperability layer with Databricks/lakehouses at the Business Data Cloud level**, per SAP's own Feb 2025 announcement ([SAP News](https://news.sap.com/2025/02/sap-databricks-open-bold-new-era-data-ai/)), and a secondary technical analysis states BDC-managed data products already land as Delta tables in HANA Data Lake Files today, with movement toward Iceberg/Polaris described as directional but not yet SAP-confirmed policy ([LinkedIn analysis, flagged as inference](https://www.linkedin.com/posts/ronaldkonijnenburg_bdc-icebergrightahead-datasphere-activity-7457154250305855488-21ze)).
- **Postgres** was not found referenced anywhere in Datasphere's own connection-type documentation as a native source; the closest generic relational options documented are **Generic JDBC**, **Microsoft SQL Server**, **Microsoft Azure SQL Database**, **Oracle**, and **SAP HANA** ([help.sap.com Connection Definition File Formats index](https://help.sap.com/docs/SAP_DATASPHERE/d0ecd6f297ac40249072a44df0549c1a/49e8be9a723c4abf842aaab6810ebf2c.html)). A Postgres-based twin would most plausibly need to go through the **Generic JDBC** connector, or export to Parquet/CSV for ingestion, rather than being natively named as a connection type — this is a **gap in the documentation, not a confirmed absence**: Generic JDBC connectors typically support arbitrary JDBC-compliant databases including Postgres, but no SAP page retrieved explicitly names Postgres.

**Practical read (inference, flagged as such):** given Parquet's status as Datasphere's default/native replication output format and its broad (if inconsistent-by-feature) read support, and given that Datasphere's own File Object Store is reported to already use Iceberg-on-Parquet internally, a twin built on **Parquet files on commodity object storage (S3/Azure Blob/GCS)** is the open-format choice best positioned to bridge into Datasphere later — via Data Flows if landing raw Parquet, or via CSV/Replication Flow if delta-load semantics are required sooner than Parquet-Replication-Flow support matures. An Iceberg- or Delta-table-native twin is plausible but currently requires either external conversion tooling or reliance on HANA Cloud's lower-level SQL import statements, neither of which was confirmed as a first-class, documented Datasphere Space ingestion path in the sources retrieved.
